# What is this repo for?
A solo project to practice an AI-driven development workflow end to end.
requirements → issues → implementation → tests → CI/CD → AWS deployment.
This repo is orchestrated with Linear and OpenAI's Symphony which enables AI agents work automatically(Codex agents and Claude Code agents).

## App description - Fraud Review Decision-Table Demo
A web app for fraud-review operators.
System recommends how to judge each of cases based on a decision table by answering Yes/No questions about a case.
Rules can also be changed through a chat interface powered by Amazon Bedrock.

> All cases and questions are fictional and AI-generated.
> They are not suitable for real fraud detection.

## Tech stack
Frontend: TypeScript, React
Backend: Python, FastAPI
E2E: Playwright
CI/CD: GitHub Actions
Infrastructure: AWS (Lambda, Aurora DSQL, Bedrock, CloudFront, CloudWatch)

## Local app development (Docker Compose)

On a fresh checkout, run the following at the repository root (where `compose.yaml` is located). Prepare Docker Engine and the Compose plugin, confirm that `docker version` can connect to the server, and confirm that `docker compose version` works. Network access is required to fetch images and dependencies. You do not need to install Node.js, Python, npm, or uv on the host, or to set app environment variables or credentials. The local development database (PostgreSQL) starts together with the app and also needs no credentials (see "Local database" below).

### Build, start together, and verify

```bash
docker compose config --quiet
docker compose build --no-cache
docker compose up -d
docker compose ps
docker compose logs --tail=50 frontend backend
```

`frontend` runs `npm run dev` in `/app` inside the container, and `backend` runs `uvicorn app.main:app --host 0.0.0.0 --port 8000` in `/app`. `db` is the development PostgreSQL, and `db-init` is a one-shot service that applies the DDL and the fictional sample data when the tables do not exist yet, then exits (`backend` starts after it succeeds). Right after startup, wait until preparation finishes, then check the following with the services running. Keep host ports 5173 and 8000 free.

| Where to check | Expected result |
| --- | --- |
| Browser: [http://localhost:5173/](http://localhost:5173/) | The heading "審査対象一覧" (list of cases to review). The list is loaded from the API (`GET /api/cases`); with no cases yet, "条件に合う案件がありません" is shown. To see a case, create one (see "Cases and judgments" below). |
| [http://localhost:8000/health](http://localhost:8000/health) | HTTP 200, JSON `{"status":"ok"}` |
| [http://localhost:8000/api/cases](http://localhost:8000/api/cases) | HTTP 200, a JSON array (empty before the first case) |

```bash
curl --fail --show-error http://localhost:5173/
curl --fail --show-error http://localhost:8000/health
```

Fetching Vite's HTML alone does not confirm that React renders, so also check the heading and description in a browser. Ports map host 5173 → container 5173 and host 8000 → container 8000.

### Cases and judgments

The screen calls the API with relative paths (`/api/...`); the Vite dev server proxies `/api` to `backend`, and in production FastAPI serves the built screen from the same origin. The screen has no intake form: cases come from the intake API or from the sample button. The API contract is in [decision-support-schema.md](docs/decision-support-schema.md).

| To get cases | How |
| --- | --- |
| Four fictional cases (2 not reviewed, 1 with a failed automatic answer, 1 registered) | `bash scripts/seed-demo-cases.sh`, then reload [http://localhost:5173/](http://localhost:5173/) |
| One case per click | The "サンプル案件を作成" button on the list (IDs like `CASE-12AB34CD`; retrying the same operation returns the same case; stored data grows with each click). See [requirements](docs/requirements.md#共有サンプル案件の作成) and [deployment steps](docs/development-workflow.md#共有サンプル案件の作成post-apisample-cases) |
| One case by hand | `POST /api/intake/cases` |
| Start over | `docker compose down -v`, then `docker compose up -d` (deletes the development database) |

A judgment is saved once per case by "判定する" (`PUT /api/cases/{id}/judgment`); a registered case is read-only when reopened.

### Administrator-AI prototype (mock, no database)

| Screen | Operates on |
| --- | --- |
| `#/admin/questions` (header link "設問管理") | Adding and retiring questions |
| `#/admin/rules` (header link "判定ルール管理") | Adding, removing and updating decision rules |

- Endpoints, validation rules and what is undecided: [admin-proposal-demo.md](docs/admin-proposal-demo.md).

### Local database

`docker compose up -d` starts a development PostgreSQL 16 (`db`) with trust authentication (no password) and **no published port**. Do not add `ports:` to `db` in `compose.yaml`.

- First start: `db-init` applies the DDL from `docs/decision-support-schema.md`, the sample questions, and rules R01–R03 (`docs/decision-support-sample.json`, `docs/decision-support-demo-rules.json`). Data lives in the volume `db_data`.
- Changed DDL or sample data is not applied automatically: run `docker compose down -v`, then `docker compose up -d` (deletes all development data).
- SQL shell: `docker compose exec db psql -U demo_admin -d decision_demo`.
- This is not Aurora DSQL, so a pass here does not show the app works there ([aws-environment.md](docs/aws-environment.md)).

### Tests and static checks inside containers

Run these at the repository root. They need no running services and no database (except the DB integration row), and each is one command. Exit code 0 is expected. Check the layers in this order, and do not move to the next layer while the previous one fails. See [testing policy](docs/testing-policy.md) for what each layer checks.

| Layer | Command |
| --- | --- |
| API contract and backend unit (no database) | `docker compose run --rm --no-deps --build backend python -m unittest discover -s tests -t .` |
| Frontend unit (Vitest + jsdom, `*.test.ts` and `*.test.tsx`; API mocked, no server connection) | `docker compose run --rm --no-deps --build frontend npm test` |
| E2E (one end-to-end flow) | `bash scripts/e2e.sh` |
| DB integration (local PostgreSQL only) | `bash scripts/backend-db-test.sh` |
| Architecture: dependency direction, backend (import-linter) | `docker compose run --rm --no-deps --build backend lint-imports` |
| Architecture: dependency direction, frontend (ESLint `no-restricted-imports`, part of lint) | `docker compose run --rm --no-deps --build frontend npm run lint` |

`--build` rebuilds the image first, because the source is copied into the image (no bind mounts). Without it, the tests may run against an old copy of the source. Tests that need the database are skipped unless `RUN_DB_TESTS=1`, which only `scripts/backend-db-test.sh` sets.

Before handing off an implementation task, run `bash scripts/review-tests.sh --feature-file <file>`, where the file holds the feature details (the issue title, description, and acceptance criteria, copied as written). It starts a separate, read-only Claude Code session that is given the feature details and the changed files (not your test results) and reviews missing frontend, backend, and E2E tests from a senior engineer's view. See the [testing policy](docs/testing-policy.md) and the [review prompt](docs/test-review-prompt.md).

After startup, run these at the same repository root. Exit code 0 is expected for all of them.

```bash
docker compose exec -T frontend npm run lint
docker compose exec -T frontend npm run build
docker compose exec -T backend ruff check .
docker compose exec -T backend ruff format --check .
docker compose exec -T backend lint-imports
docker compose exec -T backend uv pip check
```

ESLint is the lint step; Ruff does lint and a format check that does not rewrite files. The current stack has no formatter dedicated to the frontend. `npm run build` performs a TypeScript check and a Vite build. While services are stopped, you can run a one-off command by replacing `exec -T` with `run --rm --no-deps`, for example `docker compose run --rm --no-deps frontend npm run lint`.

### Reflecting changes and stopping

The current Compose setup uses no source bind mounts. The only persistent volume is `db_data` for the development database. Dependencies and source are copied into the image, so after changing files, run `docker compose up -d --build` at the root to rebuild and recreate. Files changed only inside a container are lost when it is recreated.

```bash
docker compose down        # keeps the development database
docker compose down -v     # also deletes the development database (re-created on the next up)
```

This stops and removes the services and the Compose network. Built images remain. The HTTP mock for automatic answers runs inside `backend`. Deployment to AWS and real Aurora DSQL are not part of this startup procedure.

By default, Vite's dev server accepts connections only from `localhost`, `.localhost`, and IP addresses (the default of the official Vite `server.allowedHosts`). In this repository, `allowedHosts` in `frontend/vite.config.ts` additionally allows the Compose service name `frontend` for E2E.
