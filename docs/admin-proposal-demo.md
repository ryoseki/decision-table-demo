# 管理者AIの試作（設問・判定ルールの変更案）

管理者が自然文で、設問の追加・廃止と、判定ルールの追加・削除・更新を依頼し、Before／Afterの差分を確認して、「反映しますか？」にYes／Noで答える試作です。画面は `#/admin/questions`（設問管理）と `#/admin/rules`（判定ルール管理）で、どちらを操作しているかを「操作の対象」で示します。本番の仕様ではなく、デモ限定の挙動です。

## 共通の仕組み

- 提案の生成は、既定ではモックです。Bedrockの実接続は、サーバーの設定で選びます（[接続環境](aws-environment.md)）。出力はどちらも同じ検証を通ります。
- Yesだけが、デモの一覧へ反映します。Noと承認前は、現行のデータを変えません。
- 反映先は、バックエンドのメモリ（設問A01〜A12、ルールR01〜R03が初期状態）です。再読み込みでは残り、再起動で初期状態に戻ります。審査画面のルール（`GET /api/rules`）・案件・DBは変わりません。
- 検証は、提案の生成の中で、登録の前に必ず通します。承認の入口は、サーバーが持つ検証済みの提案のIDだけで、承認の要求に追加内容は含めません。
- 提案は1回で使い切ります（Yes・Noのどちらでも）。未承認の提案は50件まで持ちます。
- 設問の決定とルールの決定は、共通のロック（`app.state.admin_lock`）で1つずつ順に行います。1つのバックエンドプロセスの中だけで成り立ちます。
- 管理者の認証・権限はありません。

| 層 | 設問 | ルール |
| --- | --- | --- |
| 提案の生成 | `question_proposer`、`bedrock_proposer` | `rule_proposer`、`bedrock_proposer` |
| 検証（純粋な関数） | `question_validation` | `rule_validation` |
| 承認と保存（メモリ） | `question_store` | `rule_store` |
| HTTP | `question_admin` | `rule_admin` |

層と依存の向きは[ARCHITECTURE.md](../ARCHITECTURE.md)を参照します。

## API

| エンドポイント | 内容 |
| --- | --- |
| `GET /api/admin/questions`、`GET /api/admin/rules` | デモの一覧（`revision`、`questions`または`rules`、`mock`、`persistence`、`source`） |
| `POST /api/admin/question-proposals`、`POST /api/admin/rule-proposals` | `{prompt}`から案を作る（201）。応答は`proposal_id`、`kind`、`before`、`after`と、操作ごとの項目。**一覧は変えない** |
| `POST .../{id}/decision` | `{decision: "yes" \| "no"}`。応答は`applied`と最新の一覧 |

| ステータス | 場合 |
| --- | --- |
| 422 | 依頼が不正、AIの出力が検証を満たさない、`decision`が不正。現行データは変えない |
| 502 / 504 | AIの応答を得られない / タイムアウト（実接続）。成功に見せない |
| 404 | 提案が未知、または承認・却下済み |
| 409 | 提案の後に基準の版が変わっている、または廃止できない設問。反映しない（提案は使い切る） |

## 設問

- **追加**: 追加できるIDは、そのときの一覧の最大番号の次だけ（A13、その後はA14、A15…と、追加のたびに増やせる。形式は`A`と2桁の数字なので、上限はA99）。廃止済みの設問も番号に数える。1回の提案で追加するのは1件で、設問文は200字以内、既存の設問と同じ文言は重複として拒否する。例: 「APIキーの失効履歴を確認する設問を追加して」→ A13。追加した設問は案件の画面に現れない。
- **廃止**: 「設問A13を廃止して」。対象に「廃止」ラベルを付け（一覧から消さない）、参照しているルールと、既存案件への影響を示す。応答は`retired`、`references`（`can_retire`）、`impact`（`unjudged`と`judged`）を持つ。
  - 現行ルールが設問を条件に1件以上持つ（デモのルール一覧も数える）ときは、Yesでも廃止しない（409）。決定の時点で調べ直す。
  - 参照がなければ、Yesで「廃止済み」にする（設問文は残す）。判定未登録の案件は新たな回答の対象外になる。保存済みの設問文と回答は、審査画面の「廃止済みの設問」で確認できる。廃止済みの設問への回答の保存は422。
  - 判定登録済みの案件は、廃止の有無にかかわらず、閲覧のみ。
  - 参照の判定は「条件にその設問があるか」だけで、旧版のルールは数えない。保存先がないアプリでは、廃止案の提案は503。
- モックの依頼: 「廃止」と設問IDを含む依頼は廃止案、「失効」と「APIキー」を含む依頼は、固定でA13の追加案を返す（A13を追加済みの一覧では、次のIDはA14になるため、検証で拒否される）。それ以外の依頼も検証で拒否される。A14以降の追加は、Bedrock実接続の生成で行う。

## 判定ルール

- **追加**: 追加できるIDは、使ったIDの最大番号の次（初期はR04）。削除したIDは再利用しない。例: 「設問A09がYes、設問A10がNoのとき注意とするルールを追加して」→ R04。
- **削除**: 「ルールR03を削除して」。削除するルールはBeforeに「削除」ラベル。
- **更新**: 「R04にA09がYesを追加して」のように、指定した既存ルールに**条件を足す**。同じIDのまま版（`revision`）が1つ進む。結果の変更、条件の削除・書き換えは扱わない。
- **検証**: 条件の設問は存在し、廃止済みでないこと。結果は4つの結果コードだけ。条件は`yes`・`no`だけ。重複（同じID、または条件と結果がすべて一致する既存ルール）は422。条件が同じで結果が違うルールは重複にしない。
- **更新の拒否**: 対象や設問がない、依頼の指定が曖昧（複数のルールID、同じ設問にYesとNo）、同じ条件の追加済み、更新後に他のルールと重複、生成の出力が依頼と食い違う。小文字のIDは正式な入力とせず、新規追加も更新も反映しない。
- **競合**: 提案は、ルール一覧の版と設問一覧の版の**両方**を基準に持つ。どちらかが変わっていたら、Yesは部分反映せず409。
- **DB構成**: 更新は共有設定の新しい版として確定し、`decision_rules`に更新後の版の行を足す。判定未登録の案件は更新後のルールで照合し、保存済みの判定の採用ルールの版・結果は変わらない。

## 定型文（ローカルの検証）

`PROPOSAL_REUSE_ENABLED=1 docker compose up --build`で、既存の開発用PostgreSQLに設定、提案、定型文を保存します。

- 入力の前後の半角スペースを除いて、登録文と完全一致したときだけ、AIを呼ばずに定型文の操作を使う（候補なし・曖昧・複数一致はBedrockへ渡す）。その時点の設問とルールで、同じ検証とYes／Noを通す。Noは取り下げ。「AIで再提案」を選ぶと、元の依頼文を生成側へ送る。
- Yesで反映した変更は、元の依頼文と検証した操作を、同じトランザクションで定型文へ自動登録する。同じ対象・文言は置き換える。Noや反映の失敗では登録しない。追加の操作は、再利用のたびに次番号を付けて検証する。
- 管理画面には、閉じた状態の「AIを経由せずに反映する変更の依頼(完全一致)」があり、登録済みの依頼を削除だけできる。削除した初期定型文は復活しない。
- 公開環境での有効化は後続。公開する前に、Bedrockへ到達する経路のアクセス・費用制限を確認する。

## 未決・未確認

- 本番の仕様: 設問・ルールの過去版、物理削除、永続保存の形式、承認の担当と運用、同じ条件で結果が異なるルールの扱いは確定していない。
- 複数のバックエンド（Lambdaの複数インスタンスなど）では、メモリもロックも共有されない。この動作は確認していない。
- 公開環境（実Bedrock・公開経路）での有効化と実機の確認は未実施。
