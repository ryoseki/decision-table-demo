# 初版の受付・モックHTTP契約と保存設計案

[要件書](requirements.md)の初版範囲（設問A01〜A12）について、受付、FastAPIのモックHTTP、取得結果の保持、保存、ルール版の扱いを、実装に渡せる粒度に具体化する提案書です。

**この文書の位置づけ（重要）**

- 第1章の「合意済み」は要件書の記述の引用・要約です。第2章以降の選択肢と推奨案、第3章の契約草案、第4章の受入条件案は、**すべて提案であり未合意**です。人の判断（第5章）が得られるまで、決定済みとして扱いません。
- 実装・テストの実行は範囲外です。アプリ、HTTP、DB、AWSでの動作は未検証です。
- 認定基準、処置、実サービスのAPI、管理者の運用は推測で確定しません。案件・利用者・問い合わせ・値はすべて架空です。
- 関連文書: [テーブル案](decision-support-schema.md)、[ワイヤーフロー案](operator-wireflow.md)、[架空データ](decision-support-sample.json)。

### 2.2 モックHTTP契約と対象設問の割り当て（提案・未合意）

**対象設問の割り当て案**

| 案 | 内容 | 影響 |
| --- | --- | --- |
| A（推奨案） | 自動回答はA09のみ。補完は案件ごとに1回。 | 受入例4・5・7の「自動回答対象の1設問」を満たす最小構成。1受付でHTTP呼び出しは自動回答1回＋補完1回。 |
| B | A01とA09。 | 受入例1〜3の入力（A01=Yes）が自動入力になり、例2の「訂正」の確認経路が増える。呼び出しが2回＋補完。 |
| C | A01〜A12すべて。 | 手入力の経路の確認が減る。1設問ずつ呼ぶため受付時に12回呼ぶ。初版の簡素さに反する。 |

割り当ては設問マスターの`auto_answer_key`で表す既存案を踏襲する（A09にキーを設定し、他は空）。設問の追加は設定の追加で足りるようにする。

**URL・入出力の草案**（バージョンは`v1`、モックであることが分かるパスにする。提案）

| 項目 | 内容 |
| --- | --- |
| 自動回答 | `POST /mock/v1/auto-answers/{question_code}` |
| 入力 | `{"user_id": "456"}`。任意で`sample_number`（整数）を渡すと偶奇判定に使う。省略時は`user_id`の整数値を使う（整数にできなければ422で、受付側では失敗扱い）。 |
| 成功応答 | 200。`{"question_code": "A09", "answer": "yes", "sample_number": 456}`。`answer`は`yes`または`no`のみ。偶数がYes、奇数がNo（設計案の規則）。 |
| 補完 | `POST /mock/v1/enrichments` |
| 入力 | `{"user_id": "456"}` |
| 成功応答 | 200。`{"user_id": "456", "account_status": "active", "plan": "free", "registered_at": "2026-09-01T10:00:00+09:00", "related_user_ids": ["457"]}`。補完はどの設問にも自動反映しない（1応答＝1設問を保つ）。 |
| 対象外の設問 | `auto_answer_key`未設定の設問コードは404。受付処理は呼ばない。 |

**失敗時の扱い（確認待ち）**

受付処理は、次のいずれかを「取得失敗」として扱い、その設問を`pending`にする。再試行はしない。

- 接続失敗、タイムアウト（仮に3秒。独自案で、実装時に調整可）
- HTTPステータスが200以外（404・422・5xxを含む）
- 応答が壊れている、`question_code`が一致しない、`answer`が`yes`・`no`以外（欠落、null、他の文字列）

補完が失敗したときは、補完の状態を`failed`として保持し、設問の回答には影響させない（補完は設問の回答ではない）。画面には「取得できていません」と表示し、再取得はしない。

**失敗の再現（受入例4用）**: 受付の入力に任意の`demo_controls.fault_questions`（例: `["A09"]`）を置き、受付処理が対象設問の呼び出しに限りモックへ失敗指示ヘッダー`X-Mock-Fault: timeout`を付ける案（推奨案）。別案は、失敗用の固定`user_id`をモック側に決めておく方法で、受付の入力は本番相当のまま保てるが、入力値と失敗の対応が暗黙になる。`demo_controls`は検証用で、実サービス接続時に削除する。

**呼び出し元と配置**: 受付処理は`MOCK_BASE_URL`（環境変数）に対して実際にHTTPで呼ぶ。FastAPIの同一アプリに`/mock/v1/`として置く案（推奨案）。ただし、Lambda上で自分自身のURLを呼ぶ構成は並行実行数、認証、URLの解決に影響する。可否は未確認で、AWS・DB接続・CD担当の確認事項とする（本書では確定しない）。

FastAPI側の事実確認: エンドポイントの失敗は`HTTPException`を送出して返し、リクエストの検証失敗は`RequestValidationError`として処理される。検証失敗の既定ステータスの記述は参照ページにないため、実装時に確認する。 [FastAPI: Handling Errors](https://fastapi.tiangolo.com/tutorial/handling-errors/)

### 2.3 受付時取得と受付APIの形（提案・未合意）

受付の入口（外部から案件を渡す想定）の草案:

| 項目 | 内容 |
| --- | --- |
| URL | `POST /api/intake/cases` |
| 入力 | `source_case_ref`、`scenario`（初版は`account_api`のみ）、`summary`、`user`、`inquiry`、任意の`period_start_at`・`period_end_at`、任意の`demo_controls` |
| 処理順 | 入力検証 → 重複確認（2.4） → 自動回答・補完のHTTP呼び出し → `review_cases`を1行保存（取得結果の保持を含む。2.6） → 応答 |
| 201 | 新規受付。`{"case_id": "...", "duplicate": false, "fetch": {...}}` |
| 200 | 重複受付。既存の`case_id`を返す。HTTPモックは呼ばない。`duplicate: true`。 |
| 422 | 入力検証エラー。案件は作らない。 |
| 取得失敗 | 受付自体は成功（201）。`fetch`に設問ごとの`status`（`ok`または`failed`）を返す。 |

画面を初めて開くときに、HTTPモックは呼ばない。

補足（提案）:

- 取得（HTTP）を先に行い保存を後にする順序では、保存の失敗後に呼び出し元が再送すると、HTTPが再度呼ばれる。これは「保存済み案件の再表示・再判定で呼び出しを増やさない」合意の範囲外だが、受付が成功するまで案件が存在しないための副作用である。許容するか、案件の保存を先にして取得中の状態を持つか（途中で止まった行の扱いが新たに必要）は、Q8で判断する。推奨案は、取得を先に行う順序を許容する。
- 同じ`source_case_ref`で内容が異なる再受付は、既存を返し、新しい内容は反映しない（200、`duplicate: true`）。内容差の検出と409は初版では行わない（推奨案。Q8）。

### 2.4 受付の重複防止（提案・未合意）

| 案 | 内容 | 影響 |
| --- | --- | --- |
| A（推奨案） | `source_case_ref`の一意制約（NULLを除く）と、保存前の存在確認。既存なら新しい案件を作らず、HTTPも呼ばず、既存`case_id`を200で返す。 | 受付を冪等にでき、「再取得しない」合意と整合する。同時に同じ参照が届いた場合は、先に保存した方が残り、後の方は一意制約で失敗して既存を返す。後の方のHTTP呼び出しは1回余分に発生しうる（まれ。許容するか第5章で判断）。 |
| B | 呼び出し側が冪等キーのヘッダーを付ける。 | 呼び出し側の協力が要る。`source_case_ref`がある以上、二重の仕組みになる。 |

### 2.5 補完値の項目と物理的な保存先（提案・未合意）

補完値の項目（2.2）のうち、保存するのは`account_status`・`plan`・`registered_at`・`related_user_ids`とする案（取得したものだけ）。

| 案 | 内容 | 影響 |
| --- | --- | --- |
| A（推奨案） | 判定済みの補完値は、新しい列`case_results.enrichment_data`（jsonb、NULL可）に、［判定する］の一括保存で書く。 | 「判定時に回答・結果と一緒に保存」する合意に合う。結果と同じ行で最新のみ保持でき、履歴は残らない。 |
| B | `review_cases`に列を足し、受付時に書く。 | 受付時の永続保存になり、合意の範囲を超える扱いになるため不採用。 |
| C | 専用テーブル`case_enrichments`を新設する。 | 項目が増えたときに拡張しやすいが、初版の少数項目には過剰。 |

書き込み元と失敗時（提案）: ［判定する］の保存処理が、サーバー側で`intake_fetch.enrichment`を読んで`enrichment_data`へ書く。画面から補完値を送らない（改変を避け、HTTPも呼ばない）。補完が`failed`のときは`enrichment_data`にNULLを書き、再表示では「取得できていません」と表示する（`case_results`があり`enrichment_data`がNULLならこの表示）。

自動回答の記録: 回答の出所（自動かオペレータの手入力か）を残すため、`case_checks.answer_source`（`auto`または`manual`、任意）の追加を提案する（推奨案）。オペレータが自動回答を訂正して保存した場合は`manual`とする。`answered_by`は［判定する］を押した担当者（初版は`OP-1`）とし、自動回答の取得時刻は2.6の保持領域に残す。追加しない場合は、出所を区別できず、画面の「自動判定済み」表示が保存後に再現できない。制約案: `answer_source`は`answer`が`yes`・`no`のときだけ非NULL（`pending`・NULLでは常にNULL）。

### 2.6 判定前の取得結果の保持と、未保存で離れたときの扱い（提案・未合意）

事実関係: 受付時にHTTPで取得してから、人が［判定する］を押すまでの間、取得結果をどこかに保持する必要がある。Lambdaは実行環境が保持されない前提で設計するため、プロセスのメモリは使えない。受付は外部からの呼び出しで、オペレータの画面は関与していないため、ブラウザにも渡せない。

**取得結果の保持先**

| 案 | 内容 | 影響 |
| --- | --- | --- |
| A（推奨案） | `review_cases.intake_fetch`（jsonb、NOT NULL、既定`{}`）に、受付時の取得結果（設問ごとの状態・回答・取得時刻、補完の状態と値）を、案件の保存と同じ1行・同じトランザクションで書く。 | 追加の表が要らず、受付の原子性を保てる。これは「受付時に取得結果をDBへ保持する」案で、合意済みの「受付時の取得だけから永続保存とは扱わない」の範囲を超えうるため、人の判断（第5章）が要る。保持するのは機械が取得した値だけで、オペレータの入力途中の値は含まない。補完値を受付時に`review_cases`へ書くため、2.5の案Bを不採用とした理由と同じ論点になる。要件書の「受付時の取得だけから、受付時にDBへ永続保存するとは扱わない」を「それだけを根拠に決めつけない」という意味に読めば許され、「保存してはならない」という意味に読めば許されない。どちらに読むかをQ5で判断する。許されない場合、2.5の案Bも同じ扱いになる。 |
| B | 専用の一時テーブルを使う。 | 分離できるが、表と削除処理が増える。 |
| C | DBに持たない。 | 保持できず、開き直すとHTTPを再度呼ぶか値を失う。再取得なしの合意に反するため不採用。 |

**画面を開いたときの表示規則（Aの場合）**

1. その案件の`case_results`がある（判定済み）なら、`case_checks`と`case_results`の保存値を表示する。`intake_fetch`は参照せず、保存されなかった設問を取得値で埋め直さない。
2. `case_results`がない（未判定）なら、`intake_fetch`の値を初期値にして、`ok`は入力済み、`failed`は「確認待ち」、対象外の設問は未回答で表示する。
3. どちらの場合もHTTPは呼ばない。

`intake_fetch`は機械が受付時に取得した値の記録で、オペレータの訂正を反映しない。［判定する］後も更新しない案を推奨するが、受付時の機械回答（例: 訂正前のYes）が`case_checks`とは別に残るため、「最新のみ保持し訂正履歴を残さない」合意に触れるとも読める。代替は、［判定する］時に`intake_fetch`の`answers`・`enrichment.data`を消し、状態（`ok`・`failed`）だけを残す案である。これもQ5で判断する。保存期間は未決で、本書では決めない。

**保存前に画面を離れて戻ったとき**

| 案 | 内容 | 影響 |
| --- | --- | --- |
| A（推奨案） | 入力途中の値は破棄する。戻ると上の表示規則どおり、最後に保存した値、または受付時の取得値を表示する。離れる際は、未保存の変更があれば警告を出す。 | 受入例6（［判定する］を押さずに開き直すと最後の保存値）に一致する。 |
| B | ブラウザの`sessionStorage`などに下書きを残す。 | 例6と矛盾し、実質的な自動保存になる。 |
| C | サーバーに下書きを保存する。 | 「入力途中の自動保存は行わない」合意に反する。 |

警告の出し方（ブラウザ標準の確認か画面内の確認か）は画面統合担当が決める。

### 2.7 ルールと設問の版、採用ルールIDの記録（提案・未合意）

**ルール・設問の版**

| 案 | 内容 | 影響 |
| --- | --- | --- |
| A（推奨案） | 初版では版を持たない。`decision_rules`は固定の架空3行（R01〜R03）を初期投入し、設問マスターは固定のA01〜A12とする。版の導入は管理者運用の合意後に別設計する。 | 業務ルールが未決の現段階で版の構造を決めずに済む。`case_results.rule_id`から当時の条件をたどれるのは、ルールが変わらない間に限る。 |
| B | `decision_rules`・`review_questions`に`ruleset_version`を足し、`case_results`に判定時の版を記録する。 | 回答時点のルールをたどれる。版の公開、進行中案件への適用が未決のため、構造だけを先に決める形になる。 |
| C | 判定時のルール条件を`case_results`へスナップショットとして複製する。 | 版なしでたどれるが、複製が増え、「最新のみ」の方針との関係を整理する必要がある。 |

注意: 現在の照合ロジックはコード内にR01〜R03を持つ。`decision_rules`に投入する値と二重管理になるため、同じ定義から投入するか、一致を確認するテストを置く（実装担当の確認事項）。保存する`result_code`は、表示名ではなくコードにする案とし、仮に`account_deletion`・`account_suspension`・`caution`・`no_issue`とする（値の確定は第5章）。

**採用ルールIDの記録（合意済みの制約を保つ）**

- 結果を選んだだけで`rule_id`を自動で記録しない。`rule_id`が記録されるのは、オペレータが開いたルール行に対して「このルールを採用」を明示的に操作したときだけとする（推奨案）。
- 採用できるのは、選択中の結果と同じ`result_code`のルール行だけとする（FKの制約と同じ）。結果と食い違う行は採用の操作を無効にする。結果を選び直して食い違いが生じたら、`rule_id`をNULLに戻す。
- グレー表示のルール行も採用の操作自体は許すか（回答と食い違うルールの採用）は、第5章で判断する。推奨案は、グレー行では採用の操作を出さない。
- 採用の操作が画面にない初版では、`rule_id`は常にNULLでよい（推奨案の最小形）。

### 3.2 `intake_fetch`の形

```json
{
  "fetched_at": "2026-10-20T13:00:00+09:00",
  "answers": {
    "A09": { "status": "ok", "answer": "yes", "sample_number": 456 }
```

### 3.3 架空例（A01〜A12の案件のみ。受入例4〜7と対応）

3案件を使う。いずれも架空である。

| 案件 | `user_id` | 受付時の自動回答（A09） | 補完 |
| --- | --- | --- | --- |
| CASE-A | 456 | 偶数のためYes | ok |
| CASE-A2 | 457 | 奇数のためNo | ok |
| CASE-A3 | 458 | `demo_controls`で失敗を指示 | ok |

**例4の受付（CASE-A3）**

```json
POST /api/intake/cases
{
  "source_case_ref": "INBOX-A3",
  "scenario": "account_api",
  "summary": "心当たりのないログインとクレジット消費について問い合わせが届いた。",
  "user": { "user_id": "458" },
  "inquiry": {
    "subject": "心当たりのないログイン",
    "body": "身に覚えのないログインとAPIキーの発行があった。（架空の問い合わせ）",
    "received_at": "2026-10-20T08:30:00+09:00",
    "identity_verified": true
  },
  "period_start_at": "2026-10-20T09:00:00+09:00",
  "period_end_at": "2026-10-20T12:00:00+09:00",
  "demo_controls": { "fault_questions": ["A09"] }
}
```

応答（201）の想定: `{"case_id": "CASE-A3", "duplicate": false, "fetch": {"answers": {"A09": {"status": "failed"}}, "enrichment": {"status": "ok"}}}`

**受入例との対応**

| 例 | 入力・操作（要件書どおり） | 本書の契約での期待（提案） |
| --- | --- | --- |
| 4 | CASE-A3でA09の取得が失敗。結果「注意」を選び［判定する］。開き直す。 | `intake_fetch.answers.A09.status`は`failed`。保存で`case_checks`のA09は`pending`（`answer_source`は`auto`ではなく未設定）、`case_results.result_code`は`caution`。開き直すと確認待ちと「注意」を表示し、他の設問は変わらない。 |
| 5 | A09を資料で確認し手入力でNo。結果「問題なし」で［判定する］。開き直す。 | A09は`no`・`answer_source=manual`、結果は`no_issue`で上書き。モックの呼び出しは増えない。`case_checks`と`case_results`には最新の値だけが残り、訂正履歴の行は作らない（受付時の機械回答の記録`intake_fetch`の扱いはQ5）。 |
| 6 | 保存後に変更し、［判定する］を押さずに開き直す。 | 最後の保存値を表示。入力途中の値はサーバー・ブラウザともに保存しない。 |
| 7 | CASE-A（`user_id` 456）。A09=Yesが入力済み。結果を選び［判定する］。開き直す。 | 保存済みのA09（`yes`・`answer_source=auto`）と結果を表示。再表示でHTTPモックの呼び出しが増えない。補完値は`enrichment_data`に保存される（例7が確認するのは回答と結果だけで、補完の保存は別に確認）。 |

**重複受付の例**: CASE-A（`source_case_ref`が`INBOX-A`）を同じ内容でもう一度受け付ける → 200、`{"case_id": "CASE-A", "duplicate": true}`。モックの呼び出しは増えず、案件は増えない。

**補完モックの例**: `POST /mock/v1/enrichments` に`{"user_id": "456"}` → 200、2.2のとおり。補完が失敗しても、`answers`の各状態は変わらない。
