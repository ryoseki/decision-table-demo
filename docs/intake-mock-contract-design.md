### 1.4 2026-11-11にユーザーが回答した内容

ユーザーがチャットで回答した内容です。Q15は、2026-11-11に「いったんOK」（暫定承認）、2026-11-12に最終承認が出ました。最終承認は、DDLの設計内容についてです。変更後のDDLは、2026-11-12にローカルのPostgreSQLと実Aurora DSQL（専用スキーマ。ユーザーがCloudShellで実行し、結果を提示）の両方で55/55成功しました（Claude Codeが実DSQLを直接観測したものではない）。

**受付と契約**

- user・inquiryの項目（Q1）: userは`user_id`のみ。inquiryは`subject`・`body`のみで、どちらも必須。`received_at`・`identity_verified`は受け取らない。
- 自動回答の対象はA09のみ（Q2）。
- モックのURL・入出力・失敗の定義は草案どおり。タイムアウトは3秒、200以外と不正な応答は失敗（Q3）。
- 失敗の再現は、受付入力の任意の`demo_controls`（Q4）。
- `subject`または`body`が無い、または空白だけの受付は拒否する（Q13）。
- 自己呼び出し（Lambda上でモックを呼ぶ構成）で進める。AWSでの動作確認は後続に引き継ぐ（Q12）。

**受付の順序（Q14）**

保存の失敗後の再送でHTTPが再び呼ばれることを避けるため、案件を先に保存し、取得を後にする。

1. 検査（不正なら422。HTTPも保存も行わない）。
2. 1回目の保存（1トランザクション）: 案件、全設問のコピー、未判定の`case_results`、A09の`case_checks`（`answer`は`pending`、`automated_answer`は空）。
3. A09のモックをHTTPで呼ぶ（タイムアウト3秒）。
4. 2回目の保存（1トランザクション）: 成功したらA09の`answer`と`automated_answer`に`yes`か`no`を入れる。失敗したら更新しない（`pending`のまま）。
5. 応答（201）。

**保存構造（Q5〜Q7、Q15）**

- 基準は、現行のテーブル案の6テーブル。
- `case_results`の`result_code`・`recorded_by`・`recorded_at`を空にできる列とし、3列は全部空か全部入っているかのどちらかにするCHECKを付ける。判定済みかどうかは`result_code`が入っているかで判断する。
- `case_checks`に`automated_answer`（`yes`・`no`のみ、空を許す）を足す。受付時の自動回答を記録する列で、受付後は更新しない。画面表示には使わない（Q7: 保存後に「自動判定済み」は出さない）。
- 補完情報を保存する列（`supplement_data`）は削除する。補完情報という概念を持たない（Q6）。補完モックは作らない。
- 受付時の取得結果を預ける列、回答の出所の列、元の案件ID列は作らない。重複受付の防止は初版の範囲外（Q8）。
- ［判定する］までの入力途中は破棄する。未保存で離れるときは警告を出す（Q9）。

**版と採用ルール（Q10、Q11）**

- ルールと設問の版は、現行のテーブル案の方式（ルール別`revision`、時刻による復元、集合の版なし）。「再判定」という概念は持たず、保存済みの案件の再保存は最新状態への上書きとして扱う。未判定の案件は復元の対象外でよい。
- 採用ルールは参考の記録で、`case_results.rule_id`・`rule_revision`に残す。結論はオペレータが選ぶ`result_code`で、採用ルールには左右されない。
- そのため、`case_results`から`decision_rules`への外部キーは外す。採用ルールの実在も、結果との一致も、DBは検査しない。`result_code`が定義済みのコードかは、保存処理（アプリ）が検査する。
- 「このルールを採用」ボタンを初版から作る。押したときだけ記録する。グレー行では押せない。

### 1.5 Q15で最終承認されたDDL変更（2026-11-12）

1. `case_results`の`result_code`・`recorded_by`・`recorded_at`を空にできる列にし、3列の全部空か全部入っているかのCHECKを付ける。
2. `case_checks`に`automated_answer`（`yes`・`no`のみ、空を許す）を足す。`CHECK (automated_answer IN ('yes','no'))`。
3. `case_results.supplement_data`を削除する。
4. `case_results`から`decision_rules`への外部キーを外す（採用ルールは参考の記録）。`rule_id`・`rule_revision`の列と、両方空か両方入っているかのCHECKは残す。これに伴い、`decision_rules`の`UNIQUE (rule_id, revision, result_code)`は不要になる。

加えて、受付時に未判定の`case_results`行を作る処理を、受付の仕様とする。

## 2. 論点ごとの整理

### 2.1 受信するuser・inquiryの項目（1.4で回答あり）

| 項目 | 内容 |
| --- | --- |
| user | `user_id`のみ（必須）。 |
| inquiry | `subject`・`body`（どちらも必須）。 |
| 受け取らない項目 | `received_at`、`identity_verified`、氏名、メールアドレスなど。 |

取り扱い:

- 受け取ったuserとinquiryは、既存の`review_cases.user_data`・`inquiry_data`（jsonb）に、定義した項目だけを保存する。定義していない項目（例: `identity_verified`、`received_at`）は無視し、保存しない。受付は通常どおり成功する（2026-11-12にユーザーが回答。必須項目の欠落や打ち間違いは、「必須項目がない」として拒否される）。
- 案件の対象期間は既存列`period_start_at`・`period_end_at`に保存する（A03・A05・A07・A09が対象期間を使う。ここは任意で、両方あるか両方ないか）。
- 元システムの案件IDは保存しない。受付の入力に含めても使わない。
- `user_id`が空、`subject`・`body`が無い、または空白だけ、型が違う場合は受付を拒否する（案件を作らない）。
- 初版の架空案件の`user_id`は整数にできる文字列に限る（モックが偶奇判定に使うため）。実サービスのID形式は決めない。
- 文字数の上限は仮に`body`4,000文字、他は256文字とする（実装時に確認。根拠となる規定は未確認の独自案で、未合意）。

### 2.2 モックHTTP契約と対象設問（1.4で回答あり）

自動回答の対象はA09のみとする。割り当ては設問マスターの`auto_answer_key`で表す既存案を踏襲する（A09にキーを設定し、他は空）。設問の追加は設定の追加で足りるようにする。1回の受付でHTTP呼び出しは1回。

**URL・入出力**（バージョンは`v1`、モックであることが分かるパスにする）

| 項目 | 内容 |
| --- | --- |
| 自動回答 | `POST /mock/v1/auto-answers/{question_code}` |
| 入力 | `{"user_id": "456"}`。任意で`sample_number`（整数）を渡すと偶奇判定に使う。省略時は`user_id`の整数値を使う（整数にできなければ422で、受付側では失敗扱い）。 |
| 成功応答 | 200。`{"question_code": "A09", "answer": "yes", "sample_number": 456}`。`answer`は`yes`または`no`のみ。偶数がYes、奇数がNo（設計案の規則）。 |
| 対象外の設問 | `auto_answer_key`未設定の設問コードは404。受付処理は呼ばない。 |

補完用のモックは作らない（Q6）。

**失敗時の扱い（確認待ち）**

受付処理は、次のいずれかを「取得失敗」として扱う。A09は`pending`のまま残り、再試行はしない。

- 接続失敗、タイムアウト（3秒）
- HTTPステータスが200以外（404・422・5xxを含む）
- 応答が壊れている、`question_code`が一致しない、`answer`が`yes`・`no`以外（欠落、null、他の文字列）

**失敗の再現（受入例4用）**: 受付の入力に任意の`demo_controls.fault_questions`（例: `["A09"]`）を置き、受付処理が対象設問の呼び出しに限りモックへ失敗指示ヘッダー`X-Mock-Fault: timeout`を付ける。`demo_controls`は検証用で、省略すれば通常の受付として動く。実サービス接続時に削除する。

**呼び出し元と配置**: 受付処理は`MOCK_BASE_URL`（環境変数）に対して実際にHTTPで呼ぶ。FastAPIの同一アプリに`/mock/v1/`として置き、自分自身を呼ぶ構成で進める（Q12）。ただし、Lambda上で自分自身のURLを呼ぶ構成は、並行実行数、認証、URLの解決に影響する。可否は未確認で、AWS・DB接続・CD担当の確認事項とする。

FastAPI側の事実確認: エンドポイントの失敗は`HTTPException`を送出して返し、リクエストの検証失敗は`RequestValidationError`として処理される。検証失敗の既定ステータスの記述は参照ページにないため、実装時に確認する。 [FastAPI: Handling Errors](https://fastapi.tiangolo.com/tutorial/handling-errors/)

### 2.3 受付APIの形と処理順（1.4で回答あり）

| 項目 | 内容 |
| --- | --- |
| URL | `POST /api/intake/cases` |
| 入力 | `summary`、`user`（`user_id`）、`inquiry`（`subject`・`body`）、任意の`period_start_at`・`period_end_at`、任意の`demo_controls` |
| 処理順 | 1.4の「受付の順序（Q14）」のとおり。検査 → 1回目の保存 → A09のHTTP呼び出し → 2回目の保存 → 応答。 |
| 201 | 受付成功。`{"case_id": "...", "answers": {"A09": "yes"}}`。失敗した場合と、2回目の保存が失敗した場合は`"pending"`。 |
| 422 | 入力検証エラー。案件は作らない。 |
| 取得失敗 | 受付自体は成功（201）。A09は`pending`のまま。 |

画面を初めて開くときに、HTTPモックは呼ばない。

保存と取得の順序についての整理:

- HTTP呼び出しは、どのトランザクションの外でも行う。トランザクションを開いたまま外部を待たない。
- 1回目の保存が失敗した場合、HTTPはまだ呼ばれていない。呼び出し元が再送しても、重複呼び出しは起きない。
- 2回目の保存が失敗した場合、A09は`pending`のまま残る。担当者が資料を見て手入力で解消できる。HTTPは再び呼ばない。
- 1回目と2回目の間は、A09が`pending`である。受付の応答が返る前の短い間で、画面から見えることはほぼない。

### 2.4 受付の重複防止（初版の範囲外。1.4で回答あり）

元システムの案件IDの列と一意制約を持たない。同じ内容が2回届くと、別の案件が2件でき、HTTPも2回呼ばれる。初版の架空案件では起きない前提とする。必要になったときは、元の案件IDの列と一意制約（NULLを除く）、または呼び出し側の冪等キーを後続で検討する（Aurora DSQLでの一意索引は未検証）。

### 2.5 補完情報と、自動回答の記録（1.4で回答あり）

**補完情報**: 補完情報という概念を持たない。保存する列も、補完モックも作らない。次は本書で決めず、後続とする。

- 要件書の「補完値を保存して再表示する」「受付時の取得だけから永続保存とは扱わない」の修正。
- ワイヤーフロー案の、不足情報を外部APIで補って表示する記述の修正。
- 他ユーザーIDの関連情報（A09〜A12）の参照方法。

**自動回答の記録**: 回答の出所（自動か手入力か）を持つ列は作らない。受付時の自動回答は、`case_checks.automated_answer`に記録する。この列は受付後に更新しないので、人が回答を変えたあとも、受付時の自動回答を見られる。画面の「自動判定済み」の表示には使わない。受付時の取得時刻は残らない。

### 2.6 受付時の回答の保存と、未保存で離れたときの扱い（1.4で回答あり）

事実関係: 受付時にHTTPで取得してから、人が［判定する］を押すまでの間、取得した回答をどこかに保持する必要がある。Lambdaは実行環境が保持されない前提で設計するため、プロセスのメモリは使えない。受付は外部からの呼び出しで、オペレータの画面は関与していないため、ブラウザにも渡せない。このため、受付時に未判定の`case_results`行を作り、A09の回答を`case_checks`に保存する。DBに持たない案は、再取得なしの合意に反するため採らない。

**画面を開いたときの表示規則**

1. その案件の`case_results.result_code`が入っている（判定済み）なら、`case_checks`と`case_results`の保存値を表示する。
2. `result_code`が空（未判定）なら、`case_checks`の`answer`を初期値にする。`yes`・`no`は入力済み、`pending`は「確認待ち」、行がない設問は未回答で表示する。
3. どちらの場合もHTTPは呼ばない。

［判定する］は、`case_results`を更新し、`case_checks`の`answer`を現在の入力で更新する。`automated_answer`は更新しない。受付時の自動回答は`automated_answer`に残るが、`answer`は上書きされ、履歴は残らない（最新のみ保持の合意どおり）。回答を空に戻す操作（選択を外す操作）は許さない。一度答えた設問は、`yes`と`no`の間で切り替えるだけで、`case_checks`の行を削除する場面はない。このため、A09の`automated_answer`は失われない。

**保存前に画面を離れて戻ったとき**

入力途中の値は破棄する。戻ると上の表示規則どおり、最後に保存した値を表示する。離れる際は、未保存の変更があれば「入力中の内容は破棄されます」と警告する。受入例6（［判定する］を押さずに開き直すと最後の保存値）に一致する。ブラウザやサーバーへの下書き保存は行わない。警告の出し方（ブラウザ標準の確認か画面内の確認か）は画面統合担当が決める。

### 2.7 ルールと設問の版、採用ルールの記録（1.4で回答あり）

**ルール・設問の版（現行のテーブル案の方式）**

- 設問: `review_questions`は現在の内容のマスターで、更新のたびに`revision`を1増やす。受付時に全設問を`case_questions`へコピーし、当時の設問文と`revision`を案件に固定する。
- ルール: `decision_rules`は`(rule_id, revision)`を主キーとする不変の行。条件を変えるときは新しい`revision`の行を追加する。
- 振り返り: 判定の日時（`recorded_at`）以前に作られた、`rule_id`ごとに最新の`revision`を引いて、当時のルール群を再現する。

この方式の制約（ユーザーは了承）:

- 「再判定」という概念は持たない。保存済みの案件の再保存は最新状態への上書きで、`recorded_at`も更新される。復元できるのは、最後の保存時点のルール群である。
- 未判定の案件（`recorded_at`が空）は、復元の対象外。
- ルール集合の版を明示的に記録する構造は持たない。必要になった場合は後続で設計する。
- 版の公開と、進行中の案件への適用は未決。

注意: 画面の照合は、`decision_rules` のルールを `GET /api/rules` で取得して使う（2026-11-14に決定。開発用DBには `docs/decision-support-demo-rules.json` のR01〜R03を入れる）。画面は、A01〜A12すべての条件を持つルールだけを扱う（一部の設問だけの条件を持つルールは、エラーにする）。バックエンドの `rule_matching.py` は、画面からは使わない。保存する`result_code`は、表示名ではなくコードにする案とし、仮に`account_deletion`・`account_suspension`・`caution`・`no_issue`とする（値の確定は未合意）。

**採用ルールの記録**

結論（案件の結果）は、オペレータが選ぶ`case_results.result_code`で、いちばん強い。採用ルールは、参考として残す記録である。

- 採用ルール`(rule_id, rule_revision)`は、オペレータが開いたルール行に「このルールを採用」を明示的に操作したときだけ記録する。結果を選んだだけでは記録しない。
- 採用しても、`result_code`は変わらない。採用したルールの結果と、選んだ結果が違っても保存できる。
- グレー表示のルール行は、採用できない（採用の操作を出さない）。
- DBは、採用ルールの実在も、結果との一致も検査しない（外部キーを外す）。`result_code`が定義済みのコードかは、保存処理（アプリ）が検査する。
- 採用ボタンは初版から作る。受入例1〜7は採用ルールを使わないため、要件書に受入例8〜10を追加した（2026-11-12にユーザーが合意。U9〜U11に対応）。

挙動の細部（2026-11-11にユーザーが確認）:

- 判定前なら、もう一度押して採用を外せる。
- 採用したあとに回答を変え、その行がグレーになったら、採用を自動で外す。
- 記録する`revision`は、画面に表示している最新のもの。

### 2.8 一覧・再表示・判定のAPI（実装済み。画面とつなぐ）

画面は、相対パス（`/api/...`）でAPIを呼ぶ。開発とE2Eでは、Vite開発サーバーが `backend` サービスへ中継し、本番は FastAPI が画面も配信するため同じオリジンになる。どの操作も、HTTPモックを呼ばない（取得は受付時の1回だけ）。保存先がDBでないとき（開発用のメモリ保存）は503。

| 操作 | 呼び出し | 応答 |
| --- | --- | --- |
| 一覧 | `GET /api/cases` | 200。配列。1行は `case_id`、`summary`、`user_id`、`inquiry`（`subject`・`body`）、`result_code`（未判定は `null`）、`counts`（`yes`・`no`・`pending`・`unanswered`）。案件がなければ空の配列。並びは案件ID順（受付日時の列がないため仮。スキーマは変更しない） |
| ルール | `GET /api/rules` | 200。配列。`rule_id` ごとに最新の `revision` の行だけで、並びは `rule_id` 順。1行は `rule_id`、`revision`、`result_code`、`conditions`（キーは設問コード、値は `yes`・`no`）。ルールがなければ空の配列。保存先がDBでなければ503。HTTPモックは呼ばない。 |
| 再表示 | `GET /api/cases/{case_id}` | 200。`case_id`、`summary`、`user`、`inquiry`、期間、設問ごとの `answer`（`yes`・`no`・`pending`。回答の行がない未回答は `null`）、`result`（未判定は `null`）。案件がなければ404 |
| 判定 | `PUT /api/cases/{case_id}/judgment` | 204。本文は `result_code`（必須）、`answers`（変更する設問だけ）、`rule_id` と `rule_revision`（両方あるときだけ記録）。不正は422（理由は `detail`）、案件がなければ404 |

- 一覧は、検索語や絞り込みなどの入力（クエリ）を取らない。絞り込みは画面側で行う。
- 一覧に、状態（登録済み・取得エラー・未審査）は含めない。画面が、結果の有無と確認待ちの件数から導く。
- `result_code` は、`account_deletion`・`account_suspension`・`caution`・`no_issue` の4つ（2026-11-12に確定）。画面の表示名（アカウント削除、アカウント一時凍結、注意、問題なし）との対応は、画面の1か所（`frontend/src/resultCodes.ts`）に置く。
