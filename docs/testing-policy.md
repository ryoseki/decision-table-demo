# テスト方針と完了の定義

機能を縦（API・画面・E2E）に作り、層ごとにテストを積む進め方を定める。要点は [AGENTS.md](../AGENTS.md)、Symphony向けの着手時チェックは `WORKFLOW.md`、コマンドの一覧と起動手順は [README](../README.md) にある。ここには、層の役割、順序、完了報告、決めた経緯を書く。

この方針は、プロジェクト独自の判断である。OpenAIのCodexとSymphonyの公式資料（2026-11-12に確認）は、AGENTS.md・WORKFLOW.mdにテストの実行方法や完了の条件を書くことを勧めるが、プロジェクト固有の完了の定義やテストの層は定めていない。

## 層と標準コマンド

| 順序 | 層 | 確認すること | 確認しないこと | DB | コマンド |
| --- | --- | --- | --- | --- | --- |
| 1 | API契約・バックエンド単体 | エンドポイントごとの、成功・入力の拒否（404・422）・拒否したときに何も変わらないこと。HTTPの入力と出力（ステータス、本文）と、照合などの論理 | DBの行、SQL、トランザクション | なし（`InMemoryCaseStore` を継承したテスト用の保存先） | `docker compose run --rm --no-deps --build backend python -m unittest discover -s tests -t .` |
| 2 | フロント単体 | **判断のロジック**（純粋な関数）と、**画面の部品**（描画して、見える内容・操作・状態の変化）。APIはモックで、サーバーに接続しない | サーバーとのつながり | なし | `docker compose run --rm --no-deps --build frontend npm test` |
| 3 | E2E | 機能の一連の流れ1本以上（例: 画面から保存し、再表示できる）。実ブラウザが必要なこと（レイアウト、実際の通信、複数サービスのつながり） | E2Eだけに任せる細かい挙動（下の層でも確認する） | あり（`docker compose` の全サービス） | `bash scripts/e2e.sh` |
| 4 | インフラのつなぎ込み | DB統合、実Aurora DSQL、Lambdaなど、つなぎ込みの部分だけ | 上の層で確認できること | 層による | DB統合は `bash scripts/backend-db-test.sh`。実DSQLは人が実行する |

- `--build` を付けるのは、ソースがイメージにコピーされる構成（バインドマウントなし）のため。付けないと、古いソースでテストが走ることがある。
- 前の段階が赤いままでは、次の段階へ進まない。E2Eで原因探しをしない。
- フロントの単体テストは、Vitest（jsdom、Testing Library）で、`frontend/src` 配下の `*.test.ts` と `*.test.tsx` を自動で拾う。画面の部品（`.tsx`）は、描画して見える内容を確認する。Node.js標準のテスト機能は `.tsx`（JSX）を扱えないため、Vitestを採用した（プロジェクト独自の判断。OpenAIの公式資料にフロントのテストフレームワークの指定はない）。依存は、公開から2週間以上経った版を、正確な版で固定する。
- `docker compose` を使うコマンドは、リポジトリのルートで実行する。

## DB統合テストの方針

- ローカルのPostgreSQLで確認するのは、**Aurora DSQLでも成り立つこと**だけ。SQLの通過、制約、保存した値の再表示、基本のロールバックなど。
- PostgreSQL固有の挙動（例: `FOR UPDATE` の行ロックで同時保存を待たせる）はテストしない。DSQLは、ロックで待たせず、衝突を検出して失敗させる方式（OCC）で、ローカルで通っても本番の挙動を保証しないため。DSQL固有の確認（OCCの再試行、行数・サイズの上限、権限）は、実DSQLで人が実行する別の確認とする。
- DB付きのテスト（`backend/tests/test_db_store.py`）は、`RUN_DB_TESTS=1` のときだけ動く。通常のbackendコンテナにも `DB_HOST` があるため、`DB_HOST` では切り替えない。`scripts/backend-db-test.sh` だけが `RUN_DB_TESTS=1` を設定する。

## 開発環境の前提

- `docker compose up` だけで、frontend・backend・開発用DBが起動し、保存と再表示まで動く。DDLと架空データは、DBの初回起動時に `db-init` が自動で適用する。
- 開発用DBはパスワードなし（trust認証）で、ホストにポートを公開しない。`compose.yaml` の `db` に `ports:` を足さない。
- DDLや架空データを更新したら `docker compose down -v` で作り直す。コンテナの作り直しだけでは再適用されない。
- 検証で作ったコンテナ・ボリュームは、自分が作ったものだけを削除する（実行ごとに一意のプロジェクト名で隔離）。
- 版の固定は、イメージはdigest、依存はハッシュ付きロック（現状維持）。

## テストの網羅（不足を防ぐ決まり）

機能を作る・変えるときは、次を守って、テストの不足を防ぐ。

1. **要件とテストを対応づける。** 受入条件・受入例・設計書の受入条件（S番号など）ごとに、確認するテスト（層とテスト名）を決める。完了報告に、この対応表（要件 → 層 → テスト）を書く。対応するテストがない項目は、未確認として明記する。
2. **挙動を洗い出す。** APIは、エンドポイントごとに、成功・入力の拒否・拒否したとき何も変わらないことを確認する。画面は、部品ごとに、描画・操作・状態の変化を確認する（ロジックだけでなく、部品のテストも書く）。
3. **E2Eで確認する挙動は、下の層でも確認する。** E2Eは細かい挙動を確認してよいが、E2Eだけに任せない。失敗の原因を速く特定するため、同じ挙動をフロント単体・API契約でも確認する。E2Eだけでよいのは、実ブラウザや実際のサービス間のつながりが必要なもの（例: 画面幅での横はみ出し）に限る。
4. **追加したものが、失敗しうることを確認する。** 確認の重さは、追加するものによって変える。
   - **新しい検査**（ESLintのルール、import-linterの契約、設定で動く検査）: **必ず1回**、違反を一時的に入れて、失敗する（直し方が表示される）ことを確認する。書き間違えると、何も検出しないまま「通過」と表示されるため。検査そのものを変えたときだけ、やり直す。
   - **新しいテスト**: 軽い確認でよい。実装の前にテストを書いて先に失敗を見る（赤 → 緑）か、実装の1行を一時的に壊して失敗を見る。特に、「〜でないこと」を確かめるアサーションは、常に真になりやすいので確認する。同じ形の既存テストへの追加は、省略してよい。
   - いずれも、リポジトリのファイルは変えない（スクラッチの場所に変更版を作り、コンテナへ読み取り専用で重ねて実行する）。
5. **PR前に、独立したレビューを受ける。** 実装タスクは、`bash scripts/review-tests.sh` で、別の新しいセッションに、テストの不足をレビューさせる（下の「テスト不足のレビュー」）。受入条件との照合は、完了報告の対応表（1）で行う。指摘は、課題の範囲内のものを直し、範囲外のものは別課題の候補として報告する。

## 静的検査（書き方・依存の向き）

テストとは別に、コードの書き方と、層の依存の向きを、機械的に検査する。違反すると失敗し、直し方がメッセージに出る。層の定義と、許される依存の向きは [ARCHITECTURE.md](../ARCHITECTURE.md) にある。

| 対象 | 検査 | コマンド |
| --- | --- | --- |
| バックエンドの書き方 | `ruff`（lint と整形の確認） | `docker compose run --rm --no-deps --build backend sh -c 'ruff check . && ruff format --check .'` |
| バックエンドの依存の向き | `import-linter`（契約は `backend/pyproject.toml`。契約の名前に直し方を書いている） | `docker compose run --rm --no-deps --build backend lint-imports` |
| フロントの書き方と依存の向き | ESLint（依存の向きは `no-restricted-imports`。メッセージに直し方を書いている） | `docker compose run --rm --no-deps --build frontend npm run lint` |

- 依存の向きの検査は、CIでも実行する。
- 検査を緩める・無視する（契約や設定の変更）のは、理由を示して人に相談する。AIが黙って緩めない。
- 新しい検査を足したら、違反を一時的に入れて、失敗することを確認する（決まり4）。

## テスト不足のレビュー（実装タスク）

実装タスク（コードやテストの変更）の完了前に、独立した新しい Claude Code セッションが、変更に対するテストの不足を、シニアエンジニアの目線でレビューする。

```bash
bash scripts/review-tests.sh --feature-file <機能の詳細のファイル>
bash scripts/review-tests.sh --feature-file <ファイル> --dry-run    # 渡すプロンプトを表示するだけ
```

- **渡す情報は、機能の詳細と、実装の内容。**
  - **機能の詳細**（`--feature-file`、必須）: 何を実装したか。Linear の課題のタイトル・説明・受入条件を、**書かれている通りにMarkdownへ転記する**。レビュー担当が、機能を理解して、あるべきテスト項目を導くため。リポジトリの外（`mktemp` や `.symphony/` の下）に置き、コミットしない。
  - **実装の内容**: 変更したファイルの一覧と、差分の統計。スクリプトが自動で付ける。
- **渡さない情報**: テストが通ったという報告、作者の自己評価、検証結果、作業メモ（課題の Agent notes や、検証結果を書いたコメントも含めない）。作者の主張に引きずられず、機能の詳細と実装から、必要なテストを自分で導かせるため。
- レビュー担当は、機能の詳細と実装の食い違い（機能の詳細にあるのに実装にない挙動、その逆）も報告する。
- 観点は、フロントエンド、バックエンド、E2E、環境・つなぎ込みの4つ。正常系・異常系・境界値・状態の遷移・拒否したとき何も変わらないこと・アサーションの強さ・層の置き場所を見る。プロンプトは [docs/test-review-prompt.md](test-review-prompt.md)。
- **読み取り専用。** 許可するのは、ファイルの読み取りと、`git diff`・`git status`・`git log`・`git show`、バックエンドとフロントのテストの実行（`docker compose run --rm --no-deps --build ...`）だけ。書き込みと、`.env` の読み取りは拒否する。そのため、「壊すと赤くなるか」を実際に確かめることはできず、読んで判断する（確かめていないものは「未確認」と書かせる）。
- 報告は、層ごとに「不足しているテスト項目」（優先度、対象の実装、不足している挙動、なぜ書くか、提案）と、弱いアサーション、確認した範囲・していない範囲。
- 指摘は、**担当が対応する**（レビュー担当はテストを書かない）。範囲内のものは直し、範囲外のものは別課題の候補として報告する。対応した内容と、対応しなかった理由を、完了報告に書く。
- 受入条件との照合は、このレビューの役割ではない。完了報告の対応表（要件 → 層 → テスト）で、別に行う。
- `claude` コマンドが使えない環境では、レビューは「未実行」と報告する。

## 着手時のチェック（受入条件）

担当Issueの受入条件を、実装の前に次の観点で確認する。

| 確認項目 | 不足の例 |
| --- | --- |
| 受入条件の各項目に、確認する層とコマンド（または手動確認）が書かれているか | 「保存できる」とだけあり、どの層かが不明 |
| APIの挙動が関わる項目に、API契約テストの条件があるか | 異常系（404・422）の記載がない |
| 画面の挙動が関わる項目に、フロント単体の条件があるか | — |
| ユーザーの一連の流れに、E2Eの条件があるか（1本で足りる） | — |
| インフラが関わる場合、つなぎ込みで確認する範囲だけが書かれているか | 「DSQLで動く」とだけある |
| 暗黙の前提が書かれているか | 「`docker compose up` で動く」「標準コマンドで通る」がない |

不足があるときは、実装の前に、不足の内容と、補う受入条件の案を示して人に相談する。

- チャットでは、止まって質問し、回答を待つ。
- Symphony経由では、実行をユーザー入力待ちで止め続けない（Symphonyの仕様）。相談事項と案をworkpadに書き、`In Review` へ引き渡して、人の回答を待つ。
- Issueの説明文は、AIが書き換えない。補う案は、workpadとチャットで示す。

## 完了報告

- 確認した層と、未確認の層を書く。受入条件の各項目を、どの層で確認したかに対応づける。
- 未確認の層が残るときは、`In Review` へ進めず、相談して待つ（上の着手時チェックと同じ扱い）。
- 例外: 人の操作や、AIが持たない資格情報が必要な層（実Aurora DSQLの確認など）は、未確認と明記して `In Review` へ進めてよい。
- 実行していない検証を、成功扱いにしない。

## 決めた経緯

保存と再表示の機能のレビューで、「`docker compose up` でDB付きで動く」「DBなしで確認できるテストがある」という期待が、どの課題の受入条件にも書かれていないことが分かった。課題が工程（設計、DB環境、実装、画面、E2E）で分かれ、つなぎ目が誰の範囲でもなかったことが原因である。この方針は、その隙間を、文書と環境で埋めるためのもの。テストの層の考え方は、テストピラミッド、契約テスト、Playwrightのベストプラクティスなどを参考にしたが、層の分け方と順序の規則はプロジェクト独自の判断である。

## 未決・未確認

- 「壊すと失敗するか」の確認を自動化する（ミューテーションテスト）かは、決めていない。実行が重くなりやすいため、必要になったときに別課題で検討する。導入や実行時間は、未確認。

- テストが0件で実行されたときの扱いは決めていない。
- CIは、ローカルと同じ unittest と `npm test` を実行するが、GitHub Actions上での実行は、PRで確認するまで未確認。
- DB統合テストをCIに載せるかは、実行時間と安定性を見てから判断する。
- 画面とAPIのつなぎ込みは、画面の統合の課題で扱う（フロントは現状APIを呼んでいない）。
