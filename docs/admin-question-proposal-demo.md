# 管理者AIの試作: 設問の追加案（モック・DBなし）

管理者が自然文で設問の**追加案**を作り、Before／Afterの差分を確認して、「反映しますか？」にYes／Noで答える最初の縦のスライスです。AIの応答はモックで、DBなしで動きます。画面は `#/admin/questions`（ヘッダーの「設問管理」）です。

## 合意した内容（2026-11-14）

| 項目 | 内容 |
| --- | --- |
| 入口 | ヘッダーの「設問管理」から、デモ専用の画面へ入る。一覧にIDと設問の文言を出し、自然文の依頼の欄を置く |
| 差分 | Before／Afterの全一覧を出す。追加行は背景色と「追加」ラベルで示す |
| Yes／No | Yesだけがデモの一覧へ反映する。Noは閉じるだけで変えない。成功は、行の表示と「デモの設問一覧に反映しました」で示す |
| 仮保存 | 反映した設問は、バックエンドのメモリに持つ。画面の再読み込みでは残り、バックエンドの再起動で初期状態（A01〜A12）に戻る。未承認のプレビューは再読み込みで破棄する |
| 例 | 架空の依頼「APIキーの失効履歴を確認する設問を追加して」→ 設問A13 |
| 対象外 | 案件の設問・回答の変更、DB、設問の削除（廃止は下の節）、判定ルールの編集、Bedrock |

## 境界（`backend/app`、層は [ARCHITECTURE.md](../ARCHITECTURE.md)）

| 境界 | モジュール | 役割 |
| --- | --- | --- |
| 提案の生成 | `question_proposer`（`MockQuestionProposer`） | 依頼から、AIの生の出力（辞書）を返す。モック。実接続（別課題）は同じ `generate` の形で差し替える |
| 検証 | `question_validation` | 純粋な関数。生の出力の形式・追加してよいID・重複・必須項目を確かめ、検証済みの提案（基準の版と一覧つき）にする |
| 承認と保存 | `question_store`（`InMemoryQuestionStore`） | 検証済みの提案と、デモの一覧を持つ。承認（版の比較と反映）をロックの中で1回にまとめて行う |
| HTTP | `question_admin` | 入力の型、ステータスへの対応。生成と保存の実装は `main` が `app.state` に置き、ここは Protocol だけを呼ぶ |

後でDBへつなぐときは、`question_store` の部分を、同じ形の別実装へ差し替える。

## API

| エンドポイント | 内容 |
| --- | --- |
| `GET /api/admin/questions` | デモの一覧（`revision`、`questions`、`mock`、`persistence`） |
| `POST /api/admin/question-proposals` | `{prompt}` から追加案を作る（201）。応答は `proposal_id`、`before`、`after`、`added`。**一覧は変えない** |
| `POST /api/admin/question-proposals/{id}/decision` | `{decision: "yes" \| "no"}`。Yesだけが反映する。応答は `applied` と最新の一覧 |

| ステータス | 場合 |
| --- | --- |
| 422 | 依頼が不正（空・長すぎる）／AIの出力が検証を満たさない（形式、許されないID、重複、必須項目）／`decision` が不正。現行データは変えない |
| 502 | AIの応答を得られない（接続エラー）。成功した応答に見せない |
| 404 | 提案が未知、または承認・却下済み（再利用できない） |
| 409 | 提案の後に一覧が変わっている（基準の版が違う）。反映しない |

- 追加してよいIDは、現行の一覧の最大番号の次（A01〜A12のときはA13）だけ。
- 承認できるのは、サーバーが持つ検証済みの提案だけ。承認の要求に追加内容は含めない（含めても無視する）。
- 検証は、単独のHTTPエンドポイントにしない。検証は提案の生成（`POST .../question-proposals`）の中で、登録の前に必ず通す。クライアントが内容を送って「検証済み」にできる口を作らないため（承認の入口を、サーバーが持つ検証済みの提案のIDだけにする）。検証の単体の確認は、純粋な関数のテストで行う。
- 承認の応答の一覧は、その時点のサーバーの最新である。Noでも、他の人の変更で一覧が進んでいれば、その最新を返す。画面は「この追加案は反映していない」と言い、一覧が変わっていないとは言わない。
- 決定（Yes・No）の通信エラーは、サーバーに届いたか分からないため、画面は反映の有無を言い切らない（提案の作成の通信エラーは、一覧を変えない操作なので「変わっていない」と言える）。
- 提案は1回で使い切る（Yes・Noのどちらでも）。未承認の提案は50件まで持つ（超えたら古いものから捨てる）。

## 設問の廃止案（同じフローへの追加）

管理者が「設問A13を廃止して」のように依頼し、差分を確認して、Yes／Noで決める。追加案と同じ画面・同じ3つのエンドポイントを使う。モック・DBなしで、ルールと案件は**読み取るだけ**で変更しない。

### 合意した内容（2026-11-15。ユーザーが確認した範囲）

| 項目 | 内容 |
| --- | --- |
| 差分 | Before／Afterの全一覧で、対象の設問に「廃止」ラベルを付ける（一覧から消さない）。あわせて、参照しているルールと、既存案件への影響を示す |
| 参照あり | 現行（最新の版）の判定ルールが、設問を条件に1件以上持つとき、参照先（ルールID・版・結果）を差分に示す。**承認でYesを選んでも廃止しない**（409）。ルールは変更しない |
| 参照なし | Yesで、デモの設問一覧で「廃止済み」にする（設問文は残す）。以後、案件の画面で新たな回答の対象外になる |
| 承認前・No | 現行のデータを変えない（一覧・ルール・案件のどれも） |
| 連鎖 | 判定ルールと案件の保存データは、自動では変更しない（無断の連鎖変更なし） |
| 判定未登録の案件 | 最新のルール（`GET /api/rules`。ルールIDごとの最新の版）で照合する。廃止済みの設問は、新たな回答の対象外。保存済みの設問文と回答は、審査画面の「廃止済みの設問」で確認できる |
| 判定登録済みの案件 | 登録時の結果と、保存済みの設問文・回答を、**閲覧のみ**で表示する（廃止の有無にかかわらず、回答・結果の変更も再保存もできない。初回の保存に成功した画面でも、開き直した画面でも同じ。2026-11-15の決定）。どの版のルールで表示するかの新しい仕様は定めない |
| 判定の登録の有無 | 案件の結果（`result`）の有無で決める。個別の設問の回答状態（確認待ちなど）ではない |

### API（追加案との差）

- 提案の作成（201）の応答に `kind`（`"add"`／`"retire"`）を付ける。廃止案の応答は、追加案の `added` の代わりに次を持つ。
  - `retired`: 廃止する設問（`id`、`text`）。`after` の対象の行は `retired: true`（廃止した設問の行だけがこの項目を持つ）。
  - `references`: 参照している現行ルール（`rule_id`、`revision`、`result_code`）と、`can_retire`（参照0件のときだけ true）。
  - `impact`: 設問を持つ既存案件を、`unjudged`（判定未登録。`case_id`、`summary`、`answer`）と `judged`（登録済み。`result_code` も持つ）に分けたもの。`answer` は保存済みの回答（yes・no・pending。未回答は null）。
  - `cascade`: 常に空（連鎖して変更するものがない）。
- 決定（Yes）は、**承認の時点の現行ルールを調べ直す**。提案を作ったあとにルールが増えて参照されるようになっていたら、409で拒否する。拒否された提案は使い切る（再利用は404）。
- 廃止の依頼は、ルールと案件の保存先を読むため、保存先がないアプリでは提案の作成が503になる（追加案は従来どおり保存先なしで動く）。
- `GET /api/cases/{id}`: 設問ごとに `retired` を付け、案件に `judged` を付ける。廃止は案件の保存データを変えず、読み出すときに印を付けるだけ。
- `PUT /api/cases/{id}/judgment`: 廃止済みの設問への回答は422で拒否し、何も保存しない（案件が登録済みかどうかにかかわらず）。保存済みの回答は変えない。判定を登録済みの案件への保存は、廃止と無関係に409で拒否し、何も変えない（2026-11-15の決定）。
- 依頼の例（モック）: 「廃止」と設問IDを含む依頼に、その設問の廃止案を返す。存在しないID・廃止済み・IDのない依頼は、検証で422。

### この範囲で確認できていないこと・衝突（未確定を確定しない）

- **E2Eのシード**: 開発用DBの案件は設問A01〜A12だけを持ち、A01〜A12は判定ルールR01〜R03がすべて参照している。「参照がなく、案件が回答を持つ設問」は、通常のデモ・開発用DBにも、アプリの経路（受付・判定の保存）にもない。そこでE2Eだけ、E2E専用のコンテナ（`compose.e2e.yaml` の `e2e-fixture`、`e2e/fixtures/seed_retirement_case.py`）が、E2E専用プロジェクトのDBに、架空の設問A13（設問文は追加案のA13と同じ）と、A13に保存済みの回答Yesを持つ判定未登録の案件を入れる。通常のデモ・本番データには入れず、テスト用のAPIも足していない。副作用として、E2Eの実行中は、シード後に受け付ける案件にもA13が入る（廃止後は「廃止済みの設問」に未回答で出る）。
- 判定登録済みの案件で、廃止した設問に**新たに回答できない**扱いにした（保存済みの回答は変えない）。2026-11-15のユーザーの決定で、判定登録済みの案件は、廃止の有無にかかわらず、そもそも再保存できない（保存済みの設問文・回答・結果を閲覧するだけ。APIも409で拒否する）。このため、登録済みの案件で廃止済みの設問に回答できないことは、この決定に含まれる。旧版の「再保存を許す既存の合意」は、この決定で置き換えた。
- 判定登録済みの案件の照合表示は、今も最新のルールで行う（既存のまま）。登録時のルール群を復元する表示は、この範囲に含めない。
- 参照の判定は、「条件にその設問があるか」だけで、条件の値（Yes／No）は見ない。旧版のルールは参照に数えない（最新の版だけ）。
- ルールの追加・削除・編集（P3）、DB・永続保存、Bedrockの実接続は、範囲外のまま。

## モックと実接続

- AIの応答は、「廃止」と設問ID（例: A13）を含む依頼にその設問の廃止案を、「失効」と「APIキー」を含む依頼にA13の追加案を返し、それ以外の依頼には操作のない出力を返す（検証で拒否される）。実際のAIではない。
- Bedrockの実接続は別課題（P4）。この試作では行わない。

## 未決・未確認（確定していない）

- 本番の仕様: 設問の過去版の保持、物理削除、廃止の永続保存の形式は、確定していない。上の「設問の廃止案」は、デモのメモリ上の挙動で、実環境の運用（承認の担当、進行中の案件への適用方法など）を決めたものではない。
- 設問の削除（物理削除）、判定ルールの追加・削除・編集（P3）、Bedrockの実接続（P4）、DBへの永続保存は、この範囲に含まない。
- 追加した設問は、案件の画面（設問A01〜A12）には現れない。案件の設問・回答には影響しない。廃止した設問は、案件がその設問を持つときだけ、案件の画面に「廃止済みの設問」として現れる。
- 管理者の認証・権限は、この試作にない（公開時のアクセス・課金リスクの対策は別に維持する）。
- 複数のバックエンド（Lambdaの複数インスタンスなど）では、メモリが共有されない。デモの仮保存であり、その動作は確認していない。
